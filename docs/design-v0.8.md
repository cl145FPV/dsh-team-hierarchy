# v0.8 设计：状态面板 / 组长复用 / 审查员 / 自主推进

四件事各自的形态、技术路径、取舍、验收标准。CEO 暂时冻结。

---

## ① 状态面板（标题栏）

### 形态

挂在 `conversation.session.header.actions`，`order: 15`（在 `subagent-catalog` 10 和 `job-list` 20 之间）。

**收起态**：一个按钮

```
● 2/5 · 34%
```

三段：在跑数 / 下级总数 / 当前会话上下文占比。占比 >60% 变黄、>80% 变红。

**展开态**：点开的浮层（必须 portal，槽位说明写了 overflow 会被裁切）

```
团队状态
● 项目经理    ctx 18.9k / 128k   ███░░░░░░░░  15%
─────────────────────────────────────────────
● lead-A      跑着   03:12   任务：重写登录模块
○ lead-B      空闲   12:40   任务：导出配置
  ● tech-C    跑着   01:05   任务：查 csc 参数
○ worker-D    空闲   02:18   任务：写 README
  ● review-E  跑着   00:42   任务：审 lead-A 的产出
─────────────────────────────────────────────
账本  7 条战线 · 5 done · 1 running · 1 blocked
```

### 为什么这个位置比悬浮球好

| | 标题栏 | 悬浮球（shell.overlay） |
| --- | --- | --- |
| 数据 | **session scope，直接读 `subagentCatalog`** | root scope，拿不到会话，得让 Host 绕一圈写快照 |
| 上下文占比 | 直接读当前会话 | 得靠 PM 主动上报 |
| 实时性 | 投影变化就刷 | 快照，PM 空闲时不动 |
| 位置 | 固定在标题栏 | 可拖 |

标题栏的代价是不能拖，但换来**数据准确、零额外管道**，值。

### 技术路径

| 数据 | 来源 |
| --- | --- |
| 子会话列表 / 状态 / 任务一句话 | `useProjection` 读 `subagentCatalog` |
| 耗时 | `useProjection` 读 `subagentTiming` |
| 当前会话上下文占比 | `useSession` 的上下文压力（字段名待确认） |
| 账本汇总 | 需要的话由 PM 写进 Host 的 `ledgerSummary` 字段；第一版可以先不显示 |

**第一版不显示每个子会话的 token**——`subagentCatalog` 不带，要另走投影，收益不值这个成本。

### 验收

- 派两条战线 → 按钮显示 `2/2`，展开看到两个组长
- 组长收工 → 状态点变空闲

## ② 组长复用

### 目标

同一条战线的后续任务不要再开新组长——省掉重新读项目现状的时间和前缀缓存。

### 现状

`delegate` 永远走 `startActivation`，每次都新建一个全新子会话。

### 形态

`delegate_to_foreman` 增加一个可选参数：

```
reuse：字符串，要接手的组长名字（team_status 里看到的那个）
```

- **不传** = 老行为，开新组长
- **传了** = 把任务用 `sendMessage` 追加给那个已存在的组长，它在原上下文里接着干

### 判定规则（写进 PM persona，由 PM 判断）

| 情况 | 做法 |
| --- | --- |
| 同一战线、组长刚收工、任务连得上 | **复用** |
| 不同战线 | 新开（复用会带着上一条战线的上下文） |
| 组长跑了 20 分钟以上，或上下文明显偏大 | 换新（轮换规则） |
| 组长报过错、被打断过 | 换新 |

PM 看得到这些：`team_status` 给状态，账本给每条战线的归属，时间从会话耗时看。

### 技术路径

1. `delegate.execute` 里判断 `args.reuse`：
   - 空 → 现有 `startActivation`
   - 有值 → `ctx.subagents.listChildren(parent.id)` 找到同名且 `mode === 'continuable'` 的子会话
2. 调 `ctx.subagents.sendMessage(parent, childId, [{type:'text', text: prompt}], { signal })`
3. 返回 `已把任务追加给 X`（不是「已派出」）

**为什么不用自动判断**：delegate 拿不到子会话的 token 和耗时，只能靠 PM 从 `team_status` 看。所以判断权交给 PM，工具只负责执行。

### 取舍

- `sendMessage` 不返回执行结果，只返回"消息被接收"。所以复用的组长"有没有真的干完"要靠完成通知或 `team_status` 确认——和现在一样。
- 复用不重置上下文，所以组长越用越脏。这就是为什么要有 20 分钟/上下文阈值。

### 验收

- 派一条战线 → 组长收工
- 再派同一条战线的收尾任务，带 `reuse: <组长名>` → 消息进那个组长，不新建会话
- 会话列表里子会话数量不增加

## ③ 审查员（全新岗位，只读，可复用）

### 形态

第六个预设 `team-review`（审查员），**旁挂**，不在链条上。

可以像组长一样**复用窗口**：同一条战线的后续审查用同一个审查员，它记得之前审过什么；换战线就新开。

### 工具集（刻意最小，且不可写）

| 工具 | 为什么 |
| --- | --- |
| 只读 fs（read / read_image） | 看代码 |
| fs-search（glob / grep） | 找引用、找同类实现 |
| pwsh | 跑测试、跑构建、`git diff` |
| jobs | 长测试放后台 |
| **无写权限** | **硬约束**：能改代码就不是审查了 |

它挂在组长的 scope 下（`delegate_to_reviewer`），PM 也能直接派（跨战线审查）。

### 复用规则

和组长共用同一套判断：

| 情况 | 做法 |
| --- | --- |
| 同一战线、上一轮审查完、现在是复核修改 | **复用**（它记得上次提了哪些问题） |
| 换战线 | 新开 |
| 审查员跑超 20 分钟 | 换新 |
| 上一轮报过错 | 换新 |

复用对审查员比对组长更有价值——它自己的问题清单还在上下文里，复核时能对着上轮逐条确认。

### persona 的核心：清单制，不是「仔细点」

「仔细检查」对 flash 无效。给结构：

**六项固定清单，每项必须给结论：**

1. **边界** — 空值 / 0 / 负数 / 超长 / 并发，各试一遍
2. **错误路径** — 每个 `await` 失败会怎样？异常被吞了吗？
3. **资源** — 文件句柄、进程、定时器有没有关？
4. **跨文件影响** — 这个函数被谁调用？改了签名有没有漏改调用方？
5. **测试真的跑了** — 不是「看起来对」，是「执行过，输出是这个」
6. **声称 vs 实际** — 汇报里说的每一句，对得上代码吗？

**输出格式锁死：**

```
| 严重度 | 文件:行号 | 问题 | 怎么改 |
| --- | --- | --- | --- |
| 高 | src/a.cs:42 | 空数组没判，会 NPE | 加 `if (x.Length == 0)` |
```

- 找不到问题 → 必须写「六项都过了，分别是…」，不许只说「没问题」
- 不许改代码，只出清单
- 不许用「建议」「可以考虑」，要么是问题要么不是

### 工作流

```
组长自己验收完
   → delegate_to_reviewer（附变更清单 + 验收证据）
   → 审查员出问题清单
   → 组长按清单修
   → 再派同一个审查员复核（复用，它对着上轮清单逐条确认）
   → 通过后组长才往上报
```

PM 只在「跨战线」或「怀疑质量」时直接派审查员。

### 取舍

- 每条战线多一次审查往返。
- **小活不值得**：只给「改动跨多文件」或「核心逻辑」的战线派。这条写进 PM persona。

### 验收

- 交一段有 bug 的代码 → 审查员在清单里指出具体行号
- 交一段正确代码 → 它不能编造问题
- 复核时能对着上轮清单逐条说「这条已修 / 这条还在」

## ④ PM 自主推进

### 目标

授权之后，PM 在没人盯的时候自己判断下一步并推进，而不是每步都等用户。

### 现状

PM 现在已经有一半自主：子会话完成会唤醒它，它自己决定下一步。缺的是**没有活跃子会话时**它不会自己动。

### 形态

用户在一个会话里明确说「自主推进」之后，PM 可以：

- 自己开新战线，不用问
- 自己决定重试/换人/砍战线
- 在等待时用 goal 机制持续工作，而不是结束这一轮

### 技术路径

**方案 A：goal 工具**（推荐）

给 PM preset 加 `@deepseek-ai/dsh-tool-goal`，PM 能 `create_goal` 立一个目标，goal 驱动会持续给它轮次直到目标完成或主动结束。

- 优点：DSH 原生机制，行为可预测
- 缺点：会一直烧 token，必须设轮次上限

**方案 B：定时唤醒**

PM 用 schedule 定时把自己叫醒检查进度。

- 缺点：空转成本高，且 schedule 是用户级功能

**选 A。**

### 授权机制

不许默认开。persona 写死：

- 只有当用户明确说「自主推进」「你不用问我」时才 `create_goal`
- 目标必须写成可判定完成的形式（"三条战线的验收标准全部通过"），不写"把项目做好"
- 设 `max_goal_rounds`，到了就停下汇报，不无限跑

### 取舍

**这是行为改变，风险最高的一条。** 无人值守的 PM 可能朝用户不想的方向推进、或者烧掉大量 token。所以：

- 默认关闭
- 必须显式授权
- 必须有轮次上限
- 每轮结束都要往账本写一行，用户回来能看懂它干了什么

### 验收

- 不授权时：PM 行为不变，不会自己开战线
- 授权后：PM 在无用户输入的情况下推进到目标完成或轮次用尽
- 每轮结束都有账本记录
